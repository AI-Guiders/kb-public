## 1. Что такое AutoShip (по коду, не по памяти)

`KbAutoShipService` — FileSystemWatcher в CdpService на корнях KB → debounce **90 с** тишины → `KbAutoShipEngine.TryShip`:

```
fetch origin → conflict-gate (origin впереди? → alert, stop) → secret-scan (IdeReviewChannel)
→ git add -A → git status → git commit → git push origin <branch>
```

Все git-команды идут через `KbAutoShipGitRunner.Run(..., timeoutMs = 30_000)` — **жёсткий 30-секундный лимит на команду**, при превышении процесс убивается и возвращается `"git timeout"`.

Алерт о провале (`AlertFail`) уходит в: (а) `Console.Error.WriteLine("[KbAutoShip] …")` — **stderr, который никто не захватывает**; (б) `CideWakeDispatch.Enqueue(..., nick: "Оператор", from: "KbAutoShip", task: "kb_autoship")` — письмо в `cdp-state.witdb → wake_envelopes`.

## 3a. Точка падения подтверждена оператором

Алерт дословно: **`fetch failed: git timeout`** → падает **первый шаг**, `git fetch origin` (не push, не конфликт, не secret-scan). `KbAutoShipGitRunner` даёт команде 30 с, затем `Kill(entireProcessTree)` и возвращает `"git timeout"`; движок оборачивает это в `fetch failed: …`.

**Следствие:** версия «структура/размер/второй remote» окончательно снята — упирается именно сетевой шаг.

**Вывод:** окружение здоровое, падение **разовое и внешнее** относительно логики движка (сетевой стопор/локальный фильтр-сканер на 30+ с), **не воспроизводится**. Точную механику без логов не установить — см. дефект 1 в §5.

## 5a. Предлагаемый патч (cdp-mcp) — по приоритетам

**P1. Сделать провал быстрым и говорящим** (`KbAutoShipGitRunner.Run`, одна точка):

```csharp
psi.RedirectStandardInput = true;            // + p.StandardInput.Close() — никто не сможет ждать ввод
psi.Environment["GIT_TERMINAL_PROMPT"] = "0";
psi.Environment["GCM_INTERACTIVE"] = "never";
psi.Environment["GIT_SSH_COMMAND"] =
    "ssh -o BatchMode=yes -o ConnectTimeout=8 -o ServerAliveInterval=5 -o ServerAliveCountMax=3 -o StrictHostKeyChecking=accept-new";
```

Эффект: сетевой стопор превращается в **явную ошибку за ~8–25 с** с конкретным stderr вместо молчаливого убийства по лимиту; интерактивный запрос становится невозможен по построению.

**P2. Лог** (`%LOCALAPPDATA%\cdp-mcp\kb-autoship.log`, append): `ts`, репозиторий, **имя шага**, args, длительность, exit, хвост stderr (≤1 КБ). Тогда следующий таймаут называет себя сам.

**P3. Настройка лимита:** `[kb.autoship] ship_timeout_ms = 30000` (+ отдельный `fetch_timeout_ms`, потому что fetch — сетевой шаг, а commit — локальный).

**P4. Один повтор для `fetch`** через 5 с (и/или перевзвод debounce при провале с backoff): разовый стопор лечится без человека.

**P5 (по желанию). Отдельная страховка, к этому инциденту НЕ относится** (fetch wissance не касается). Отделить вердикт от вторичного pushurl: «primary ok, secondary failed» → состояние `ShippedPartial`, а не `Failed`.

**P0 (сделано вне cdp-mcp).** Диагностический скрипт `scripts/diagnose-kb-ship.ps1` теперь бьёт каждый сетевой шаг **жёсткой границей** (`-HardLimitSec`, по умолчанию 40 с): проба не может повесить сессию, а повисший шаг помечается как `ПОВИС >N c` — это и есть след, который иначе теряется, как потерялся у меня на одном прогоне.

## 5b. Нужен ли `fetch` вообще? (вопрос оператора: «репо личный, никто кроме меня не коммитит»)

**Зачем он там по замыслу.** Не против людей, а против **расхождения двух копий одного канона**: если `origin/main` уехал вперёд, движок останавливается и зовёт оператора — потому что авто-rebase/auto-merge на markdown-каноне запрещён по ADR-0224 («operator must reconcile (no auto-rebase)»). Для безопасности самого push он не нужен: git и так отклоняет non-fast-forward, и этот случай в движке уже обработан (`push rejected: … conflict: true`).

**Что говорит история репозитория.** Гейт задуман под другую эпоху — и она была реальной:

| Факт | Значение |
|---|---|
| merge-коммиты | **23**, среди них `Merge github/main`, `Merge remote-tracking branch 'origin/main'`, `Merge remote-tracking branch 'upstream/main'` (апрель–май 2026) |
| последний такой merge | **2026-05-13** |
| внешний автор (`kanapylka`) | последний коммит **2026-03-07**, всего 31 |
| локальные клоны личного канона | **нет** (group-kb клоны указывают на другой репо — `AI-Guiders/kb`) |
| с 2026-05-13 | линейная история с одной машины |

То есть: сейчас «кроме меня никто» — **правда по фактам**; но гейт создавался, когда был форк/орг-контур с upstream-мержами.

**Настоящая проблема — не нужность, а место.** В `KbAutoShipEngine` порядок такой (номера строк):

```
33  fetch origin          ← сетевой шаг
37  rev-list HEAD..origin/main
48  secret-scan
53  add -A
57  status --porcelain
60  if clean → return Clean      ← «нечего отправлять» проверяется ПОСЛЕ сети
64  commit
68  push origin main
```

Следствия:
1. **Сеть дёргается на каждое FS-событие**, даже когда отправлять нечего (touch файла, перезапись тем же содержимым, временный файл) → движок может выдать `fetch failed` при **пустом дереве**. Именно это делает ошибку абсурдной на вид.
2. **Симметричная дыра:** если коммит прошёл, а **push** упал — дерево чистое, следующий триггер дойдёт до строки 60, вернёт `Clean` и **ничего не отправит**. «Закоммичено, но не отправлено» застревает навсегда так же, как сегодняшний fetch.

**Предложение (дополняет §5a):**

| # | Правка | Эффект |
|---|---|---|
| **P6a** | `status --porcelain` **первым**; пусто → `Clean`, сети нет вообще | убирает весь класс шумных алертов на пустом дереве |
| **P6b** | `fetch` — **советующий, не ворота**: провал → в лог, продолжаем; арбитр — `push` | сегодняшний алерт просто не возник бы; расхождение ловится отклонённым push |
| **P6c** | (по вкусу) убрать `fetch` совсем: `add → status(clean?) → commit → push` | проще всего; при одно-машинной реальности почти ничего не теряем |
| **P6d** | периодический тик / проверка «HEAD впереди `origin/main`» → повтор `push` | закрывает дыру 2 (иначе повтор не сработает никогда) |

**Итог:** fetch — страховка на эпоху форков, которая сейчас не работает, зато первой ловит сетевой стопор и берёт вину на себя. Правильный ход — **P6a + P6b** (fetch остаётся как ранняя диагностика, но перестаёт быть узким местом), P6c — на усмотрение оператора.

## 8. Второй класс отказов: гонка за `.git/index.lock` (2026-10-17, 00:0x)

**Симптом (алерт оператору):** `git add failed: … Unable to create 'D:/Experiments/agent-notes/.git/index.lock': File exists.` — то есть «не может создать lock, file exists».

**Механизм:** `git add` берёт эксклюзивный `.git/index.lock`; второй писатель в тот же репозиторий получает именно это сообщение. AutoShip оборачивает его в `git add failed: …` и шлёт алерт.

**Причина — наша, и конкретно моя.** За 12 часов в KB-репозитории: **6 коммитов вручную** (сессия `opencode-plugins`) **против 5 от AutoShip** — два писателя в одном репо, причём debounce AutoShip взводится на каждое моего же файлового события:

```
5cf47a7d KB(cdp-mcp): …             ← вручную
1f5b3371 KB(L0/A): …                ← вручную
6ac97f36 KB auto: …                 ← AutoShip
09ad1b03 KB: autoship — нужен ли…    ← вручную
648e9d01 KB: autoship — уточнение…   ← вручную
551d7b2b KB: autoship timeout — …    ← вручную
09ce2c14 KB: autoship timeout разбор ← вручную
12aea800 KB auto: …                  ← AutoShip
77831ddb KB auto: …                  ← AutoShip
bf557e27 KB auto: …                  ← AutoShip
96070a34 KB auto: …                  ← AutoShip
```

**Нарушенное правило (канон, дословно):** `domains/agent-operations/playbook-cursor-coordinator-local-workers.md`
- стр. 44: `└─ KB edits → **KbAutoShip** watcher (no manual push)`;
- стр. 116: `**KB** — не руками; ждём/включаем KbAutoShip watcher`;
- стр. 154: `| Worker push KB «чтобы закрыть» | KbAutoShip должен; ручной push только code repos |`.

Найдено уже **после** починки `public-cut` и после перехода на данные (A). Диff `agent-notes.md` в 00:0x:

```

+<!-- section:recall-facade-probe -->
```

Автоматический пробник recall-фасада **вставляет секцию с тем же `section_id` в самое начало файла** и заодно **дописывает BOM** (`-<!-- … -->` → `+﻿<!-- … -->`). Это объясняет три вещи:

1. **Дубликаты `section_id`** — три были склеены вручную (994–1004), через час снова две: нарушение `hot-agent-notes-split-invariant` §16 **воспроизводится каждым прогоном пробника**;
2. **«Дрожащий» верх канона** — каждое срабатывание сдвигает L0 вниз и меняет первую строку;
3. **Откуда BOM** — его добавляет пробник, а не человек (BOM даёт мусорные диффы `-<!-- … -->` / `+﻿<!-- … -->`).

**Почему это больше не ломает публикацию (проверка A):** состав берётся из `kb-public-agent-notes.include`, а не из позиции маркера. Гейт на уже «подпорченном» пробником файле: `OK: публикуемый набор согласован (12 секций; дубликат — предупреждение, а не отказ)`, потому что дубликат пробника лежит **вне** публикуемого набора.

**Источник найден и починен (2026-10-17, 01:0x):** это **тест** `CdpMcp.Tests/RecallKnowledgeFacadeTests.cs` — интеграционный против **живого** канона (`TryInit` читает реальный `D:/agent-notes-mcp/agent-notes-mcp.toml`). Тест `Auto_hot_only_query_falls_through_to_hot` писал пробу с **фиксированным** `section_id`, отсюда дубликаты (четыре блока к 17.10) и BOM от пути записи.

**Фикс:** id уникален на прогон (`recall-facade-probe-<8 hex>`), файл восстанавливается в `finally` байт-в-байт без BOM. **Проверено:** прогон класса (7 тестов) — SHA256 канона **до == после**; прогон полного набора (2289 тестов, 0 падений) больше канон не трогает.
